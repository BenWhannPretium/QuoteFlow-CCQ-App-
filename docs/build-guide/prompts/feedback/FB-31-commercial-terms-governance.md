## Build

### A. Payment-terms approval routes (N19-07)
1. **Config** `app_setting.terms_exception_routes` (provisional, validated in `config-admin/settings.ts`): an ordered list of tiers `{ codes: string[], approverPermission, documentRequired }`. `approverPermission` is chosen from an allow-list of permission keys (the existing `terms.exception.decide` and the new one below); an unknown key, an empty code list or a code outside `requested_payment_terms` is rejected. A non-standard code that matches no tier falls to the first tier (today's behaviour, so nothing is ever without an approver).
2. **A second permission** in `matrix.ts`: `terms.exception.decide.senior`, granted to **Leadership** only (the closest existing role to the CFO Sarah named; **do not add a role**: that is Entra work and Ben's call). Document in the PR and the matrix comment that "CFO" is the stated approver, Leadership is a stand-in, and replacing it is a config and matrix change once the right role exists. Allowed and denied tests for every role on both permissions.
3. **Seed, provisional, and only a guess from one sentence of the meeting:** `NET_45` to the pricing lead (what happens today); `NET_60`, `NET_90`, `NET_120` and `OTHER` to the senior permission with `documentRequired: true`. State in the setting's description and in the PR that Sarah and Oleg have not set thresholds and that this seed exists so the mechanism can be shown, not as policy.
4. **Enforcement on the server.** `decideTermsException` requires the deciding user to hold the permission the quote's tier names, and a user may not decide an exception they requested. **No requester bar exists today** (`decideTermsException`, `services/commercial.ts` ~975-1060), and the pricing lead holds `terms.edit` and is the only Net 45 decider, so a bar there could leave no one able to decide: add the bar only for tiers whose approver differs from the requester's roles, and put the pricing-lead-requests-and-decides case to Ben as a question. The pricing lead can no longer decide a senior-tier request; the response says whose decision it is. **The route as it stands declares `config.permission: 'terms.exception.decide'` (`routes/v1/commercial.ts` ~149), which is checked before the handler, so Leadership holding only the senior permission would be refused with 403:** change the declared permission to the check the codebase uses for routes whose permission depends on the record (verify; the service then enforces the tier), update the registry entry and the route inventory, and note that `canDecide` is computed at `services/commercial.ts` ~397. A new permission also touches the CHECK constraints `role_permission_permission_check` and `gate_definition_decider_permission_check` (0050 regenerated them: follow it) and the `role_permission` rows for existing environments. Record the tier's permission on the request when it opens (a new nullable text column on `terms_exception_request`, Fabric-safe) so a later config change does not reroute an open request silently; set it for existing pending rows in the migration from the then-current config, and say in the PR that **open requests for Net 60 and above now wait for Leadership** (no notification is back-filled; **no list of pending exceptions exists anywhere and Leadership lacks `terms.edit`**, so without a notice Leadership cannot find an open request except through its quote link: if a small "Payment-terms exceptions waiting for you" list on the approvals page is cheap, add it, otherwise cut it and say so; and put the back-fill to Ben as a question).
5. **`documentRequired`.** A request in such a tier needs more than a note: the rationale (at most 1,000 characters, already required) **and** a supporting document attached to the quote, of a new attachment kind `payment_terms_approval` (follow how FB-24 and FB-26 added kinds: `attachment_kinds_by_place`, the registry above, not `accepted-formats.ts`, which only derives hint text; the migration must replace the `attachment_kind_check` constraint; versioned like `cer_proof` if that fits). The deciding screen shows it and the decision cannot be approved without one. **Cut line:** if the attachment kind proves larger than a day of work, build it as a rationale of at least 100 characters (a setting) plus a required "Formal documentation is on file; where" text answer, and list the attachment kind as not built.
6. **Who is told.** The request's notification goes to the holders of the tier's permission (`recipients.ts`), not always the pricing lead; the in-app and email text, the quote's timeline entry and the intake chip say who decides ("Waiting for Leadership", "Non-standard: Pricing will review" becomes "Non-standard: needs approval by <role label>" from the tier). **There is no roles table or role-label catalogue** (only `role_permission` and the web's `landings.ts` `roleLabel`): put the approver's display label in the tier config. Other places that hard-code "pricing lead" for this decision and must read the tier instead: `g4-checks.ts` ~133-134, `CommercialPanel.tsx` ~245, ~323 and ~456, `TermsException.tsx` ~15, ~20 and ~77, `render.ts` ~336, and the `g4_required_checks` description in `settings.ts` ~179. No string is hard-coded per tier.
7. **Intake and the Commercial tab** show, when a KAM picks a non-standard code, plainly that it needs approval and by whom, and that documentation is needed if the tier says so. The G4 check `terms_exception` is unchanged.
