## What the code does today (read 2026-11-16; verify before relying on it)
- **After Final Review:** `planProposalRelease` (`packages/domain/src/final-review/release.ts`) sets `quote.proposal_issued_at` and `validity_until` on G4 Approve; the quote moves to **Customer Decision** and the KAM is told "Approved; issue the proposal." Nothing produces the document the KAM sends. "My proposals" (`/proposals`) lists the quotes waiting for the customer.
- **Price figures:** FB-14's `model_summary` and `model_summary_field` hold the fields read from a `cost_model` / `roi_model` upload, per `app_setting.model_summary_templates`. The **costing map is seeded inactive** (the pre-makeover ERF layout; `Summary` sheet, first variant in column B: total cost B13, **target price B16**, annual volume B22, capital block V22–V24). **That map reads one variant only**; the new costing template from Pricing (Gemma Cebolla) has not arrived. `app_setting.model_summary_visible` switches the figures on or off.
- **Items:** FB-19's `quote_item` (label, container size, volume, standard description) and each item's `eng_review` (plant `plant_code`).
- **Terms:** `quote.price_basis`, `freight_type`, `requested_payment_terms`, `terms_*` (FB-08 and FB-11); `validity_until`; the customer is the Salesforce Account (read through the integration). **No customer part number and no customer contact exist in the schema.**
- **Files:** versioned `attachment` rows (kinds in `packages/domain/src/attachments/file-types.ts`; `QUOTING_MODEL_KINDS`), stored through the B-16 service (SharePoint via Graph; a fake in dev and tests).

## Build

### 1. Data model (migration 0048, additive)
- **`offer_letter`** (quote child; one row per generated letter): `id` uuid v7, `quote_id`, `quote_version`, `letter_no` smallint (1…n per quote), `attachment_id` (the stored `.docx`), `template_version` text, `wording_approved` boolean (the setting's value when generated), `letter_date` date, `attention` text (≤ 120), `valid_until` date, `cost_model_attachment_id` and `cost_model_version` (which workbook the prices were read from), `generated_by`, `generated_at`. RLS as a quote child (the three policies of `0042_fb14_model_summary.sql`, enabled and forced).
- **`offer_letter_item`** (one row per item on the letter): `offer_letter_id`, `quote_item_id`, `item_no`, `part_description`, `part_number` text (≤ 60, typed by the KAM), `place_of_manufacture` (the plant label), `annual_volume`, and the **snapshotted** `piece_price_per_1000`, `mold_charge`, `change_parts_charge` as `numeric(18,4)`, null when not on the letter. Same RLS. Snapshotting means a later costing upload cannot change a letter already sent.
- **Fabric-safe (rule 10):** no `jsonb`, no arrays, `numeric` ≤ 38. Add the analytics view only if you need one; if so, its T-SQL twin in `packages/db/sql/fabric/`. Run `pnpm db:dictionary`.
- **New attachment kind `offer_letter`:** added to the kinds, the file-type allow-list (`.docx`, with the existing type sniffing and size limit), and the B-16 storage. One current letter per quote is **not** enforced: every generation is a new version, older ones stay downloadable and are labelled **Superseded** when `quote_version` differs from the quote's current one.

### 2. Prices from the costing workbook (extends FB-14; read `packages/domain/src/model-summary` and `apps/api/src/services/model-summary.ts` first)
- **Per-item fields.** A model-summary map field gets an optional `itemNo` (null = the whole quote). `model_summary_field` gets a nullable `item_no smallint`. Everything else in FB-14 is unchanged: server-side, cached values only, no formula evaluation, failure never blocks the upload.
- **Offer fields.** Add three field keys any costing map may carry per item: `offer_piece_price`, `offer_mold_charge`, `offer_change_parts_charge`, each with a `unit` of `usd_per_unit` or `usd_per_1000` (a pure domain function converts to **per 1,000** with exact decimal arithmetic; unit-tested). A key with no value for an item is "not in the workbook".
- **Seed values.** In the **inactive** pre-makeover costing map add `offer_piece_price` for item 1 **only** where `costing-template-structure.md` names a candidate cell (the target price, `Summary!B16`). **Do not guess its unit**: seed `usd_per_unit`, mark it proposed, and put the question to Gemma. Leave the mold and change-parts fields unmapped (no candidate cell exists). The map stays `active: false`; an Admin turns it on. The **new** costing template's cell map is **not built** (the template has not arrived).
- **Prove it on a synthetic costing workbook** with three variants (one column each), a map active **in the test only**, with prices for all three items.
- **Which workbook.** The letter reads the **current** `cost_model` version's summary, and only when its status is `complete` and `model_summary_visible` is on. Otherwise the readiness check (Build 3) says: "The costing workbook has no readable price summary (<FB-14 reason>). Ask Pricing to fix the workbook or an Admin to set up the template."

### 3. The letter (domain, API, document)
- **Domain (`packages/domain/src/offer-letter/`, pure, no I/O, 100% unit-tested):**
  - `evaluateOfferReadiness(facts, config)` → `{ canGenerate, blockers[], warnings[] }`. **Blockers:** the quote is not in Customer Decision, is on hold, or has no `proposal_issued_at` / `validity_until`; no complete costing summary; **an item without `offer_piece_price`**; a *required* offer row missing for any item (config `required` flags, seeded piece price **required**, molds **required** when the quote's tooling funding is customer-paid or shared and otherwise optional, change parts optional); an item with no plant; a `cost_model` uploaded **after** the G4 approval (`offer_letter_block_if_costing_changed`, seeded **on**: the price may have changed since Final Review). **Warnings (advisory):** the wording is unapproved; no Attention name; no Part # for an item.
  - `buildOfferLetterModel(facts, inputs, config)` → a plain data model (header lines, one row per item, the assumptions list, the closing). **No docx types in the domain.**
  - Optional rows (config) that have no value are **omitted**, never printed as zero, "N/A" or blank.
- **Config (`app_setting.offer_letter_template`, provisional, editable by an Admin without a deploy, validated like `model_summary_templates`):** the title ("Offer Letter"), the introduction and closing paragraphs, the **pricing-assumptions list** (each item a sentence), the row labels and `required` flags, and `show_validity`. Seed the wording **from the old template's real text**, marked `provisional: true` and `legal_approved: false`, then adjusted only where the old text is plainly wrong for FB-08 / FB-11 terms (note every change as a deviation). **Whitelisted tokens only:** `{{quoteNumber}}`, `{{customerName}}`, `{{validUntil}}`, `{{paymentTerms}}`, `{{priceBasis}}`, `{{freight}}`, `{{toolingFunding}}`, `{{moldOwnership}}`. A sentence that uses a token with no value on the quote is **dropped**, not printed with a hole in it. A setting `offer_letter_wording_approved` (seed **false**) records Legal's sign-off.
- **Where each field comes from** (write this table in the plan and the structure note; none is typed except the two marked):

  | Letter field | Source |
  |---|---|
  | To | the Salesforce Account name on the quote (the customer, never "End User") |
  | Attention | **typed by the KAM** on the generate screen (nothing to pre-fill from; see "Waiting on") |
  | Date | the proposal-issued date (`proposal_issued_at`, US Central) |
  | Valid until | `validity_until` (shown when `show_validity`) |
  | Quote # | `CCQ-YYYY-NNNNN` |
  | Part description | the item's label and standard description |
  | Part # | **typed by the KAM per item** (no field exists; do **not** add one to intake) |
  | Place of manufacture | the item's plant label (Engineering's decision, value list) |
  | Estimated annual volume | the item's volume |
  | Piece price per 1,000 / Molds / Change parts | the costing summary, converted to per 1,000 where needed |
  | Pricing assumptions | config paragraphs plus tokens (payment terms, price basis and freight, tooling funding) |
- **The unapproved-wording flag.** While `offer_letter_wording_approved` is false, the document's **header** carries "DRAFT: wording not yet approved by Legal" in the brand's warning colour on every page, and the generate screen shows a warning banner. When an Admin flips the setting, new letters lose the line. A letter records the value it was made with (`wording_approved`).
- **Renderer (`apps/api/src/documents/offer-letter-docx.ts`):** takes the domain model, returns a `Buffer`. The visual design follows the **current Pretium brand standards** (logo, colours, fonts, spacing, header and footer, page number, the pricing table's styling) from the `pretium-branding` skill. Brand tokens live in one file (`documents/brand.ts`), not scattered through the renderer. **Font:** use the brand's document font if a standard Pretium Word install has it, otherwise a safe fallback (Arial) and say which in the PR. US Letter, Word-editable (the KAM may adjust before sending). A **pricing table with one row per item** when there are several, columns Item, Place of manufacture, Estimated annual volume, Piece price per 1,000 pcs, Molds, Change parts (omit a column no item has).
- **Routes (all under `/api/v1/quotes/:quoteNumber`, all in OpenAPI, every one declaring its permission):**
  - `GET /offer-letter`: the readiness, the prefilled letter model, the sources ("Read from <file> v<n>, uploaded by <name> on <date>"), the previous letters. Needs `offer.read` (every role that can read the quote).
  - `POST /offer-letter`: body `{ attention, items: [{ itemId, partNumber }], acknowledgedWarnings }`. Re-evaluates readiness **on the server** inside a transaction that locks the quote row (a letter is never made from a stale check), snapshots the prices, renders, stores the file as an `offer_letter` attachment, writes the `offer_letter` rows, an `offer_letter.generated` **audit event** (letter id, quote version, item count, template version, `wording_approved`, the costing file and version; **not the prices or any customer text**) and an `offer_letter_generated` timeline event. Needs the new **`offer.generate`** (provisional: KAM on **own** quotes, SalesLeader, Pricing, PricingLead, Admin; update `matrix.ts`, `01-architecture.md` §3.4 and `docs/security/route-inventory.md`; confirm with Bailey).
  - **Download** goes through the existing attachment download route, which already audits each download and enforces data scope.
- **Never email or send the letter from QuoteFlow** (sending on a user's behalf is its own design; see "Left for later").
