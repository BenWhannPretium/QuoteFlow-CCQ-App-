# FB-21 to FB-27 · Ground rules and close-out (read by every step)

Each FB-21 to FB-27 prompt says "Follow `FB-21-to-27-ground-rules.md`". Read this file in full before you plan. Where a prompt and this file disagree, the prompt wins for its own step.

## Before you start
- **Start from the latest `origin/main`** in a fresh branch named in your prompt. Read `CLAUDE.md` (non-negotiable rules 1–11), then `docs/build-guide/01-architecture.md`, `docs/build-guide/03-build-steps.md` → "Nov 17 and 18 feedback (FB-21 to FB-27)" (the run order and which step owns which files), and `docs/build-guide/04-decisions-and-risks.md` §2a.
- **Read `docs/build-guide/feedback/inputs/feedback-2026-11-17.md`.** It is the record of what was asked (the N17 and N18 IDs), who asked, and the triage Ben agreed. Nothing else from the meetings is in the repo; do not look for the transcripts or the worksheets.
- **Verify before you build.** Every "What the code does today" note in a prompt was read from `main` at `f017ccc` on 2026-11-18. Other FB steps may have merged since. Re-read every file you change. If the code differs from a note, follow the code and record the difference as a deviation. Never build on a note you have not checked.
- **Stay in your lane.** Your prompt lists the files other steps own while you run. Do not edit them except where your prompt allows it; if you must, keep the change minimal and say so in the PR.

## While you build
- **Authorization on the server.** Every changed or new route declares its permission through `packages/domain/src/policy`. Add permission-matrix tests that check **allowed and denied for every role**: KAM, SalesLeader, EngLead, Engineer, ProductionScheduler, Pricing, PricingLead, Finance, Approver, Leadership, Admin, PostAward. Keep `docs/security/route-inventory.md` current (its test fails otherwise). The UI may hide things; it is never the control.
- **No hard-coded open rules (rule 4).** Lists, labels, thresholds, messages, required-field sets, defaults and mappings go in config tables or app settings, seeded `provisional: true`. Change config in existing environments with a **data migration** that leaves a row alone when the business has approved it (`approved_at` set) or an Admin has edited it (follow `0044_fb15_intake_fixes.sql`, `0046_fb17_gate_decisions_holds.sql` and `0036_fb09_value_lists_other.sql`). A workflow rule (`gate_outcome_definition.required_fields`) is config too: change the seed in `packages/domain/src/workflow/seeds/hybrid.ts` **and** add a guarded `UPDATE` for existing environments. Editing a seed alone does not reach existing environments.
- **Audit everything** a user changes (append-only `audit_event`). Never update or delete audit rows.
- **Fabric-safe schema (rule 10).**
  - A new `jsonb` or array column gets a `<column>_json text` companion: register it in `packages/db/src/fabric.ts`, then add the column, the `zz_fabric_json` trigger argument and a backfill in the migration. Companions stay out of the Drizzle schema.
  - Every `numeric` has precision ≤ 38. No `inet`, `interval`, range, `tsvector` or geometric types; use `text`.
  - No partitioning, no `TRUNCATE`. **Deprecate columns; never drop them.**
  - A new analytics view needs a T-SQL twin in `packages/db/sql/fabric/`.
  - The guard tests (`fabricCompat.test.ts`, `fabricTwins.test.ts`, `test/fabric.int.test.ts`) must pass. Run `pnpm db:dictionary` when the schema changes.
- **Migrations.** The last migration on 2026-11-18 is `0048_fb20_offer_letter.sql`. Use the next free number when you start (`ls packages/db/migrations`). Several FB steps run in parallel and each may add one. Before you open the PR for review, `git fetch origin main`; if a migration has landed, rebase and renumber yours (the file name, `meta/NNNN_snapshot.json`, and `idx` / `tag` in `meta/_journal.json`), then re-run the integration tests.
- **Synthetic data only (rule 8).** No real customer, opportunity, price or person data in code, seeds, fixtures, screenshots or the PR. People's names already in the build guide may be used in docs.
- **Tests come with the feature.** Domain rules → Vitest unit tests. Routes → permission-matrix and integration tests on a real Postgres. UI → at least one Playwright happy path for each changed stage. Check the changed screens at 1366 × 768 and at 390 px wide, in light and dark themes, with axe clean (UX-018 set this bar; do not regress it: keyboard reachable, focus visible, targets ≥ 24 px, no sideways scroll at 320 px).
- **Words on screen** are plain and short, in the words the people in the meeting used. Screen text is code; business rules, lists and letter wording are config.
- **When something is genuinely missing** (a list, a name, a link, a Salesforce field), do not invent it. Build the mechanism, leave the value provisional, empty or switched off, list it in the PR under "Waiting on", and build the rest.

## Before you open the PR
- **Run `pnpm verify`** (lint, typecheck, unit, integration, build) with `docker compose up -d db`. If the session can't run Docker, use a local Postgres 16, or say so in the PR and let CI run the integration tests. Fix every failure you caused. **Never skip, delete or weaken a test to get green.** A test may change only because the behaviour it checks was deliberately changed; list each such test in the PR.
- On Windows, use Node 22 (not 24) and never rewrite files with `Get-Content -Raw` (it mangles UTF-8).
- **Git.** Conventional Commits (`feat(pricing): …`), small logical commits, a **draft** PR that fills the repo's PR template. Do not put any AI model name in commits, code comments or the PR.
