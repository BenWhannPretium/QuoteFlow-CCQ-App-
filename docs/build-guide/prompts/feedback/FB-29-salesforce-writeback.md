## Build

### A. A write interface that cannot be reached by accident
1. New `SalesforceWriter` interface (its own file, not on `SalesforceReader`): `updateOpportunity(sfOpportunityId, fields, { dedupeKey })` returning `{ ok: true } | { ok: false, retryable, code, message }`, and `getCurrentStage(sfOpportunityId)` read **through the writer's own session**. The Salesforce REST update has **no idempotency key** and jsforce's `update` returns only `{ id, success, errors }` (no modstamp): the key is local only (the outbox's `dedupe_key`), and a retry is made safe by reading the current value first, not by a server-side key. Only `Opportunity` fields named in the **write allow-list** may be passed; the writer refuses any other object or field. **Put the allow-list in a new writer-side file (`writeMap.ts`), not in `fieldMap.ts`** (FB-32 owns `fieldMap.ts`) **and never add it to `MAPPED_OBJECTS`** (that map drives the reader's describe, its SELECTs and the `fieldMap.test.ts` scan).
2. `JsforceSalesforceWriter` (the real one, a separate file using the same auth module with its **own** credentials: `SF_WRITE_CLIENT_ID`, `SF_WRITE_CLIENT_SECRET`, `SF_WRITE_LOGIN_URL`, all optional; **client credentials only** (no JWT variables); `SF_WRITE_LOGIN_URL` has **no default** (`SF_LOGIN_URL` defaults to `https://test.salesforce.com`, which would silently satisfy the sandbox test below), and the writer's config refuses `test.salesforce.com` with client credentials exactly as the reader's does (`config.ts` ~184-196); the read-only user is never reused) and `FakeSalesforceWriter` (records every call; failures and timeouts can be injected). Factory `createSalesforceWriter` on **`SF_WRITE_MODE`** = `off` (default) | `fake` | `live`, in a writer file (not in `create.ts`, the reader's factory, which stays under the read-only guard).
3. **Guards in `config.ts` (with tests):** `live` is refused unless the write credentials are set **and** either `APP_ENVIRONMENT=prod` or the login URL is recognizably a Salesforce **sandbox** (a My Domain host containing `.sandbox.`; `test.salesforce.com` is refused for client credentials); the `instanceUrl` the token response returns must pass the same check before any write; `fake` is refused when `APP_ENVIRONMENT=prod`; `live` is always refused when `SF_MODE` is `fake`. The message must say why, in plain words.
4. Narrow the three read-only guards as described above: the `no-restricted-syntax` block in `eslint.config.js` covers `files: ['src/salesforce/**/*.ts']`, so add a **later override that switches the rule off for the writer files only** (as `oauth.ts` is exempted), and keep `create.ts` and every reader file guarded. Add a test that fails if a write method appears in any file other than the writer files.
5. **One org.** On the test site the reader points at the production org. The regression check and any pre-read of the current stage use the **writer's own session** (`getCurrentStage`), never the reader, so a sandbox writer is never compared against production data.

### B. Configuration (rule 4): switched off, provisional
Settings seeded `provisional: true` in `packages/db/seeds/config/settings.ts`, validated in `packages/domain/src/config-admin/settings.ts`, and inserted for existing environments by the migration (only where absent; an Admin's value is kept):
- `sf_writeback_enabled` = `false` (the master switch).
- `sf_writeback_mode` = `dry_run` (`dry_run` records what would be sent and sends nothing; `live` sends). Switching to `live` requires the environment guards in A.3 to allow it, and is refused with the reason otherwise.
- `sf_writeback_map`: a list of `{ event, enabled, sfObject: 'Opportunity', sfField, value }` entries. Events: `outcome_recorded` (value from `sf_outcome_stage_names` via `sfStageForOutcome`; `sfField` `StageName`; **enabled**, as the one thing everyone already named: F-035 "stage and outcome"; **only for a decision at the customer-decision stage**, `gate.stageKey === CUSTOMER_DECISION_STAGE_KEY`, the existing `atCustomer` test at `gateService.ts` ~239, because `sf_outcome_stage_names` is keyed by the bare outcome key and G6 also has a `requote` outcome that would otherwise map to "Quoting"; the G6 advance (`AWARDED`) and stop have no seeded stage, so nothing is written for them), `stage_changed` (value from a QuoteFlow-stage-to-Salesforce-stage table you add to the same setting; seeded **empty**, so disabled), `quote_link` (QuoteFlow quote number and link into a custom text field; `sfField` **null**, so disabled). Validation rejects an entry whose `sfField` is not in the write allow-list in `writeMap.ts` (A.1; never `fieldMap.ts`, which FB-32 owns) (so a typo or a price field cannot be configured).
- `sf_writeback_stage_regression` = `skip` (do not move a Salesforce opportunity to an earlier stage than its current one; `allow` is the alternative): Salesforce is the front door and a sales person may have moved it further.
- Nothing is hard-coded: stage names, fields, the retry delays and the maximum attempts (`sf_writeback_max_attempts`, seed 5) are settings.

### C. A durable queue, written in the decision's own transaction
1. New table `sf_writeback_outbox` (migration 0056; Fabric-safe: payload and response as `text`, no jsonb or arrays, numeric precision under 38; RLS and grants like `notification`; no `TRUNCATE`): id (uuid v7), `quote_id`, `sf_opportunity_id`, `event`, `sf_object`, `sf_field`, `value` (text), `payload` (text, the JSON that would be sent), `dedupe_key` (unique: quote, event, target value, and the transition's id), `status` (`pending` | `sent` | `failed` | `skipped` | `dry_run`), `attempts`, `next_attempt_at`, `sent_at`, `failed_at`, `last_error` (text, at most 500 characters, no tokens), `skipped_reason`, `created_at`, `created_by`. A partial index for due `pending` rows. Add the audit actions you need (a migration changes the constraint) or reuse existing ones with the entity `sf_writeback`; say which in the notes.
2. **Enqueue inside `GateService.decide`'s transaction**, right after the notifications, through one small service function. Only when `sf_writeback_enabled` is true and the event has an enabled map entry with a target. If the map or a value is invalid, **skip, log, and write an audit row**; never throw, because a configuration error must not abort a user's gate decision. **A caught error is not enough inside a Postgres transaction:** a failed INSERT (a unique or CHECK violation) puts the whole transaction in the aborted state (25P02) even if you catch it. So validate everything before the insert, insert with `ON CONFLICT (dedupe_key) DO NOTHING`, and if anything else could fail, wrap the insert in a savepoint. A rolled-back decision leaves no row. **Never close an opportunity another quote still needs.** The map entry for `outcome_recorded` carries a `closing` flag (seeded true for the lost and expired outcomes, whose Salesforce stages close the opportunity). Before enqueueing, and again in the worker before sending, a `closing` write is **skipped with reason `other_active_quote`** when another QuoteFlow quote that is not closed, or an open re-quote draft (`quote_draft.requote_of_quote_id`), is linked to the same `sf_opportunity_id`. The linked re-quote (`requote.ts` ~209-214) records G5 "expired" through `gates.decide` and, in the same transaction, creates a new draft on the same opportunity: that is exactly this case, so closing the opportunity there would be wrong. Verify the path and test it. **The other order matters too:** `LINKED_REQUOTE_STATES` is `closed_expired` and `open_lapsed` (`packages/domain/src/outcome/requote.ts` ~23), and from `closed_expired` the service creates only the draft and records **no gate decision**, so the closing write may already have been sent when a re-quote starts later. Add an event `requote_started`, enqueued where the re-quote draft is created, with the value taken from the `requote` entry of `sf_outcome_stage_names` ("Quoting" in the seed): it **reopens** the opportunity. It is exempt from the `sf_writeback_stage_regression` skip (a reopen is deliberately a move backwards, so give that map entry a `reopens` flag), it supersedes a still-pending closing write for the same opportunity, and it is skipped when QuoteFlow has written nothing closing for that opportunity. **It is sent only if Salesforce still holds the closed stage QuoteFlow wrote:** the worker reads the current stage through the writer's session (`getCurrentStage`) and compares it with the closing value QuoteFlow last sent for that opportunity; if a sales person has since moved the opportunity on (for example to "Negotiating" or "Closed Won"), the reopen is `skipped` with reason `moved_in_salesforce` and audited, never forced. The `closed_lost` flag suppression (see `sf_status_flag` above) also holds while an open re-quote exists on the opportunity. In `dry_run` the row is created with status `dry_run` and is never sent.
3. **Worker** `jobs/sfWriteback.ts`: every minute under a new advisory lock id, claim due `pending` rows with `FOR UPDATE SKIP LOCKED`, and for each opportunity send only the **latest** pending value per field (mark older ones `skipped` with reason `superseded`). With `sf_writeback_stage_regression = skip`, read the current stage first (through the writer's session, per A.5) and mark the row `skipped` if sending would move backwards, or if Salesforce already has the value. Success: `sent`. A retryable failure: back off (1 minute, 5, 30, 2 hours, 6 hours; from settings) up to the maximum, then `failed` and **notify each Admin once** (the sync-failure notice, `sfSync.alertOwners`, is type `integration.failed`, in-app only and has no dedupe key: add a type or title of your own for write-back and give it a `dedupeKey` made from the outbox row id). A non-retryable failure: `failed` at once. The worker never touches the quote.
4. **Audit** (append-only, rule 3): enqueue, send, skip, fail, Admin retry and Admin skip each write a row with what was sent or why not (field names and values; nothing secret).
