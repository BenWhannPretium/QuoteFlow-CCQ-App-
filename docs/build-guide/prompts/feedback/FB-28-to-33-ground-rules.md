# FB-28 to FB-33 · Ground rules for every build session (read first)

Each FB-28 to FB-33 prompt says "Follow `FB-28-to-33-ground-rules.md`". Read this file in full before you plan. Where a prompt and this file disagree, the prompt wins for its own step. These rules replace `FB-21-to-27-ground-rules.md` for these steps; they keep most of it and change four things: how migrations are numbered and timed (the 2026-11-19 outage), who merges, where the close-out notes go, and how several sessions share one machine.

## Who does what
- **You build one step and open one draft PR.** You do **not** merge it and you do **not** mark it ready unless your prompt says so. An orchestrator session merges PRs, in an order it chooses, after it has read your report and CI is green.
- You were started by an orchestrator. You may be sent follow-up messages (a CI failure to fix, a rebase, a question). Do what the message says for your own branch only.
- Never touch another session's branch, worktree or database. Never use bare `git stash`. Never force-push to `main`; force-push your own branch only after a rebase (`--force-with-lease`).

## Before you start
- **Start from the latest `origin/main`** in a fresh branch named in your prompt: `git fetch origin && git switch -c <branch> origin/main`. Read `CLAUDE.md` (rules 1 to 12 and the 2026-11-19 write-back decision), then `docs/build-guide/01-architecture.md`, `docs/build-guide/03-build-steps.md` → "Nov 19 feedback (FB-28 to FB-33)" and `docs/build-guide/04-decisions-and-risks.md` §2a.
- **Read `docs/build-guide/feedback/inputs/feedback-2026-11-19.md`.** It is the record of what was asked (the N19 IDs), by whom, and what was decided. Nothing else from the meeting is in the repo; do not look for transcripts.
- **Verify before you build.** Every "What the code does today" note in a prompt was read from `main` at `c9ea359` on 2026-11-19 by someone who did not run the app. Other steps may have merged since. Re-read every file you change. If the code differs from a note, follow the code and record the difference as a deviation. Never build on a note you have not checked. A note marked **unverified** is a question, not a fact.
- **Stay in your lane.** Your prompt lists the files you own and the files other steps own while you run. Do not edit theirs; if you must, keep the change to a line or two and say so in the PR.

## While you build
- **Authorization on the server.** Every changed or new route declares its permission through `packages/domain/src/policy`. Add permission-matrix tests that check **allowed and denied for every role**: KAM, SalesLeader, EngLead, Engineer, ProductionScheduler, Pricing, PricingLead, Finance, Approver, Leadership, Admin, PostAward. Keep `docs/security/route-inventory.md` current (its test fails otherwise). The UI may hide things; it is never the control.
- **No hard-coded open rules (rule 4).** Lists, labels, thresholds, messages, required-field sets, defaults, mappings and approval levels go in config tables or app settings, seeded `provisional: true`. Change config in existing environments with a **data migration** that leaves a row alone when the business has approved it (`approved_at` set) or an Admin has edited it (follow `0044_fb15_intake_fixes.sql`, `0046_fb17_gate_decisions_holds.sql`, `0036_fb09_value_lists_other.sql`, `0049_fb21_capital_readiness.sql`). A workflow rule (`gate_outcome_definition.required_fields`) is config too: change the seed in `packages/domain/src/workflow/seeds/hybrid.ts` **and** add a guarded `UPDATE` for existing environments. Editing a seed alone does not reach existing environments.
- **Audit everything** a user or the system changes (append-only `audit_event`). Never update or delete audit rows.
- **Fabric-safe schema (rule 10).** A new `jsonb` or array column gets a `<column>_json text` companion registered in `packages/db/src/fabric.ts`, with the column, the `zz_fabric_json` trigger argument and a backfill in the migration; companions stay out of the Drizzle schema. Every `numeric` has precision 38 or less. No `inet`, `interval`, range, `tsvector` or geometric types. No partitioning, no `TRUNCATE`. **Deprecate columns; never drop them.** A new analytics view needs a T-SQL twin in `packages/db/sql/fabric/`. Run `pnpm db:dictionary` when the schema changes. The guard tests (`fabricCompat.test.ts`, `fabricTwins.test.ts`, `test/fabric.int.test.ts`) must pass.
- **Synthetic data only (rule 8).** No real customer, opportunity, price or person data in code, seeds, fixtures, screenshots or the PR. People's names already in the build guide may be used in docs.
- **Tests come with the feature.** Domain rules: Vitest unit tests. Routes: permission-matrix and integration tests on a real Postgres. UI: at least one Playwright happy path for each changed stage. Check changed screens at 1366 × 768 and at 390 px wide, in light and dark themes, with axe clean (UX-018 set this bar: keyboard reachable, focus visible, targets of at least 24 px, no sideways scroll at 320 px).
- **Words on screen** are plain and short, in the words the people in the meeting used. Screen text is code; business rules, lists and letter wording are config.
- **When something is genuinely missing** (a list, a name, a link, a Salesforce field, a permission), do not invent it. Build the mechanism, leave the value provisional, empty or switched off, list it in the PR under "Waiting on", and build the rest.

## Migrations: number, timestamp, upgrade path (this is what broke the test site on 2026-11-19)
Drizzle applies a migration only when its journal `when` is later than the newest one already applied. On 2026-11-19 a hand-set future `when` made the test database skip two migrations; the API then failed at start-up and every deploy failed for 7.5 hours. CI did not see it, because CI migrates an **empty** database. See `04-decisions-and-risks.md` BR-18 and CLAUDE.md rule 12.
1. **Your number and `when` are assigned in your prompt** (the orchestrator assigns them so parallel steps never collide). They are a starting point: **the first migration PR to merge keeps its number; each later one renumbers.** The last migration on `main` at `c9ea359` is `0055_fb23_engineering_cost_packout.sql` with `when` 1795150000002.
2. Before you open the PR for review, and again if the orchestrator tells you another migration has landed: `git fetch origin`, then look at `origin/main`'s `packages/db/migrations/meta/_journal.json`. If a migration you did not expect is there, rebase, renumber yours (file name, `meta/NNNN_snapshot.json`, `idx` and `tag` in the journal) and set its `when` to **the largest `when` in the journal on `origin/main` plus 1** (the orchestrator's rebase message gives the number and the floor; **a `when` that was ever merged to `main`, including one later reverted, is never reused**, because a revert does not un-apply a migration on the test database). Never use the clock, never a hand-set future date. `drizzle-kit generate` writes the clock: always overwrite its `when`.
3. **Prove the upgrade path, not only the empty path.** Once FB-28 has merged, `pnpm release:upgrade-check` does exactly this: use it. Before that, do it by hand: create an empty database; apply **`origin/main`'s migrations folder only** (write `origin/main`'s `packages/db/migrations/` to a scratch directory with `git archive`, and apply it with drizzle's `migrate()`; do **not** use `runMigrations` for this, because it also applies *your* schema's `COMMENT ON` statements and views to a base-migrated database and fails with 42703 on any added column); then run your branch's `pnpm db:migrate` against the same database; then `pnpm build`, start the API as the App Service does, `DATABASE_URL=… PORT=<yours> AUTH_MODE=dev NODE_ENV=test node apps/api/dist/azureStart.js` (it migrates, seeds config and starts the server; `server.js` alone does neither), and call `/api/v1/health` for `"status":"ok"` and `"db":"up"`. Report what you ran in the PR.
4. A migration never edits an applied migration's SQL and never assumes a table exists that an earlier one in the same PR did not create. Write each statement to be safe to re-run where cheap (`IF NOT EXISTS`).

## Several sessions on one machine
- **Node 22, not 24.** The default `node` is v24 and the repo refuses it. Prepend `C:\Users\benwh\AppData\Roaming\fnm\node-versions\v22.23.3\installation` to `PATH` in every shell call before `pnpm`.
- **Your own Postgres.** Docker is often not running, and other sessions are using port 5432. Use the port named in your prompt. If `docker ps` works, use `docker compose` with a project name of your own and your port. Otherwise start a throwaway Postgres 16 from `C:\Program Files\PostgreSQL\16\bin`: `initdb -D <scratchpad>/pgdata -U ccq --pwfile=<file holding ccq> -A scram-sha-256 -E UTF8`; `pg_ctl -D <scratchpad>/pgdata -o "-p <your port> -c max_connections=200" -l <scratchpad>/pg.log start` (run it in the background); create databases `ccq` and `ccq_test`. Point `DATABASE_URL` and `TEST_DATABASE_URL` at your port in your shell only. Stop it with `pg_ctl ... stop -m fast` when you finish.
- **Your own ports, or you will test another session's code.** `apps/web/e2e/playwright.config.ts` starts servers with `reuseExistingServer: !process.env.CI`, so if two sessions use the default ports (3100, 3101, 4173) one silently runs its tests against the other's server and database. Set `E2E_PORT`, `E2E_DEV_API_PORT` and `E2E_WEB_PORT` to the three numbers in your prompt in every shell that runs Playwright, and, for a hand-started dev server, use **API `PORT` = your `E2E_PORT` + 2** and **Vite `--port` = your `E2E_WEB_PORT` + 10**, with `VITE_API_PROXY_TARGET=http://localhost:<that API port>` (Vite's proxy otherwise points at port 3000, `apps/web/vite.config.ts`). Never start anything on 5432, 5173, 3000, 3100, 3101 or 4173. Before a Playwright run, check nothing is already listening on your three ports.
- **Run the whole suite once, late.** While you work, run the tests for the files you touch (`pnpm --filter <pkg> test <file>`), `pnpm lint` and `pnpm typecheck`. Run the full `pnpm verify` once, when the code is done, because the api integration suite takes about 18 minutes and four other sessions are using the same CPU. CI on Linux is the arbiter: fix every failure you caused; never skip, delete or weaken a test to get green. A test may change only because the behaviour it checks was deliberately changed; list each such test in the PR.
- **Known local-only flake:** the pricing-history `.xlsx` tests (`pricing-history.int.test.ts` "refuses a file that is not the export", `packages/integrations` `exportReader.test.ts`, the import at the start of `pricing.spec.ts`) fail intermittently on this Windows machine and pass on CI. Do not chase them unless you changed that reader.
- **Windows text.** Never round-trip a repo file through `Get-Content -Raw`: it mangles UTF-8. Use the Edit and Write tools, or `[IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)` and `WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))`. After a scripted change, check `git diff` for non-ASCII changes.
- **Git.** Conventional Commits (`feat(pricing): …`), small logical commits, a **draft** PR that fills the repo's PR template (`.github/pull_request_template.md`). Do not put an AI model name in code, comments, docs or the PR text.

## Close-out: write one file, not the shared docs (do this last, in the same PR)
Several PRs run in parallel, and the shared docs (the build steps, decisions, change logs) are append-heavy, so they conflict on every merge. **Do not edit these shared files:** `03-build-steps.md`, `04-decisions-and-risks.md` (except a row your prompt names), `05-path-to-mvp.md`, `feedback-change-log.md`, `feedback/QuoteFlow Change Log.csv`, `feedback/inputs/feedback-2026-11-19.md`. The orchestrator consolidates them in one docs PR after the last merge. Instead write **`docs/build-guide/feedback/closeout/FB-<n>.md`** with these sections, and update only the topical docs your change touches (`01-architecture.md` §4 workflow, §3.4 roles, §4.3 notifications, §5 data model, §6 integrations; `docs/uat/scripts/`; `docs/uat/quickstart/`: the in-app help page is generated, so edit `docs/uat/quickstart/print.html` and run `UPDATE_QUICKSTART=1 pnpm --filter @ccq/web test`; `docs/security/route-inventory.md`; the data dictionary):
1. **Step entry** for `03-build-steps.md`: the "Done when" list with boxes ticked, then **"Built <YYYY-MM-DD>. Notes and deviations:"**: the migration number, anything built differently from the prompt and why, every provisional value seeded, what was cut, what is waiting on whom, the tests that changed because behaviour changed, and what you verified and where (local or CI).
2. **Provisional values FB-<n> seeded**: a table (value, seed, waits on, who signs off) for `04` §2a.
3. **One sentence** for `05-path-to-mvp.md` §1, the "User feedback updates" row.
4. **Change-log rows**, one per N19 item you addressed, as a Markdown table fragment with the columns **Date** (today, US Central) · **Type** `Build change` · **Step** · **Change** (what was built, in words a KAM or engineer understands) · **Feedback IDs** · **Raised by** (names and function, from the record) · **Rationale** (the feedback, why built this way, what was deliberately not done, any provisional value awaiting sign-off) · **Status** `In PR` · **PR / commit**; and the same rows as RFC 4180 CSV lines (header `Date,Type,Step,Change,Feedback IDs,Raised by,Rationale,Status,PR`).
5. **Proposed tracker rows**, one tab-separated Build Backlog row per N19 item (ID `F-___`, source "CCQ MVP Demo and Open Decisions (Nov 19)", area, title, type, detail, raised by, status `In Progress`, build note with the PR link). Never edit `QuoteFlow Feedback Tracker.xlsx`.
6. **Questions for Ben to send** (draft them; send nothing yourself, to nobody).
