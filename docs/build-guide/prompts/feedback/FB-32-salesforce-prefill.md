## What the code does today (read 2026-11-19 at `c9ea359`; verify before relying on it)
- **Prefilled today** (`prefillFromOpportunity`, `apps/web/src/intake/model.ts` ~565-640; `itemFromSpec` ~646; server reads in `apps/api/src/services/salesforce.ts`): the opportunity (picked), the customer (Account id and name, never typed; "not yet a Pretium customer" is entered in QuoteFlow), the ship-to (tried in order from the provisional `ship_to_sources`: the first item's product spec `Ship_To_City__c`, `Ship_To_State__c`, `Shipping_Country__c`, then the Account's shipping address; an override needs a reason; the opportunity's free-text `Ship_to_Locations__c` is shown beside it and never parsed), resin (`Resin_Type__c`, matched to a value-list code by `matchCode`), neck diameter and finish (`Neck_Finish__c`, parsed by `neckFromSalesforce`), annual volume (`Line_Annual_Volume__c`), container size (`Capacity__c`, free text), item label in "Add from Salesforce products" (spec `Name`, else `Capacity__c`), estimated annual revenue (`Opportunity.Amount`, skipped when flagged `amount_suspect`), close date (displayed only, not stored). Each pre-filled field shows a "from Salesforce" tag and a "Use the Salesforce value" link (`Steps.tsx` ~454-482). The tag and undo come from `sfPrefill`, which is defined in `packages/contracts/src/intake.ts` (~72-81, persisted and bounded; shared with FB-31): giving item 1's label a tag means adding a `label` key there and handling it in `ITEM_KEYS` and `draftItems`; keep that change to those lines. Re-picking the opportunity must not overwrite a label the KAM typed.
- **Not prefilled, though the map has them:** `Product_Type__c` (`PRODUCT_SPEC_FIELDS.productType` is read by `mapper.ts` ~165 and the synthetic fixture builder, and carried on the `SfProductSpec` DTO, which has **no consumer in the app**; `color` is already on the DTO, so no mapper change is needed) and `Color__c` (mapped, unused; the QuoteFlow colour is its own list). **Item 1's label is not filled from Salesforce** (only items added from the Salesforce products are).
- **Entered only in QuoteFlow, with no Salesforce source mapped:** request class, product family and components, market and sub-market (`W13-04`: Salesforce moved them to the product record: `OpportunityLineItem` / `Product2`, names pending from Zachary), PCR, additives, colour, decoration, dimensions, gram weight, mold, drawing, RFP link, dates ("quote needed by", "product needed by"), payment terms, tooling funding, stocking, price basis and freight, packaging, bid reference, comments.
- **Where the mapping lives:** code only. `fieldMap.ts` is "the only place Salesforce object and field names live"; there is no config table and no Admin field-map screen. To add a field: a `std()` or `custom()` entry in `fieldMap.ts` (a custom field the org's `describe()` lacks is dropped to null), map it in `mapper.ts` and the DTO in `packages/contracts`, add a snapshot column and migration only if a typed column is needed (otherwise read it from the snapshot's `raw`), run the live contract test, then Admin → Integrations → **Full re-sync**. Product specs are **not** synced: they are read live per opportunity and cached for 60 seconds. `fieldMap.test.ts` forbids mapping any price, cost, margin, revenue or capital field.
- **Users and structure:** no KAM-to-sales-leader relationship exists (`app_user`, roles from Entra; a SalesLeader sees all quotes); Salesforce's `User` and `ManagerId` are never read. **Visibility today:** the default scope is `all`; the picker has "Mine" (default) and "All"; with scope `all` a KAM can switch to All and start a quote on **another KAM's** opportunity (the new quote's KAM is the person picking). **Setting an Admin scope would not stop this:** `default_scope_type` and the `owner` scope limit only which *quotes* a user sees; the picker's "Mine" is a search filter (`services/salesforce.ts` ~187) and nothing checks the opportunity's owner against the caller when a quote is started. Enforcing Darren's "correct" needs a new server-side check of the opportunity owner against the user (matching an Entra identity to a Salesforce owner is itself uncertain: the picker matches on email, the UPN, or the first 8 characters of the UPN's local part). On 2026-11-19 Zachary asked whether a KAM can only move forward with their own opportunities and Darren Miller answered "correct". **That is a policy and security decision for Ben (N19-06). Do not change it here;** put it in the PR as the first question.

## Build

### A. A prefill map instead of code in two functions
A small module in `packages/domain/src/intake/` (pure, no I/O) describing each Salesforce-to-QuoteFlow field: `{ quoteflowField, sfSource, kind: 'fill' | 'suggest', match: 'valueList:<key>' | 'text' | 'neck' }`, and the functions that apply it, so `prefillFromOpportunity` and `itemFromSpec` read the map instead of repeating the logic. Existing behaviour does not change (resin, neck, volume, container, label, ship-to, revenue); a test per existing field proves it. Adding a confirmed field later is one entry here plus one in `fieldMap.ts`.

### B. The wins that need no answer
1. **Item 1's label** is filled from the first product spec (its `Name`, else `Capacity__c`), as "Add from Salesforce products" already does, only while the KAM has not typed one; tagged "from Salesforce", with the usual undo.
2. Anything else you find, **only** if it is already mapped, its meaning is not in doubt, and a value-list match is exact. List what you considered and did not do.

### C. Suggestions, not fills, for the two unused fields (switched off)
For `Product_Type__c` and `Color__c`: when a setting `intake_sf_suggestions_enabled` (provisional, seeded **false**, inserted by migration 0058 where absent) is on, show a one-line hint under the QuoteFlow question you choose **after the describe** (the candidates are the `product_family` list for `Product_Type__c` and the `color_type` list for `Color__c`, **but matching either is itself a guess about what the Salesforce field means**; the synthetic fixture happens to set `productType` equal to `productFamily`, which proves nothing). If the describe does not make the meaning clear, build the mechanism and leave that hint out, and say so: "Salesforce says <value>" with a **Use this** button, only when the value matches an entry of that question's list exactly (case-insensitive, trimmed, on the entry's code or label). **`matchCode` (`intake/model.ts` ~550) is not exported and is not exact:** it lowercases and strips every non-alphanumeric character, so "Wal-Mart" equals "walmart". Export it, or move it into the new domain module, and add a stricter helper for this feature or say in the PR that you used the looser one and why; never fill automatically, never block, never write. Label the hint with Salesforce's own field label when a describe gave you one, not your reading of what it means. In the PR say what a describe showed (the field label, type and picklist values) and give a recommendation for Ben and Zachary about whether the setting should be switched on. Tests: off shows nothing; on shows the hint for an exact match, nothing for a miss, and "Use this" fills and tags it.
